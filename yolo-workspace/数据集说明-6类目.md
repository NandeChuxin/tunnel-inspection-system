# 6 类目训练数据集说明（dataset-6class）

> 生成脚本：`tools/yolo/build-6class.js`　核验脚本：`tools/yolo/verify-6class.js`
> 核验报告：`核验报告-数据集-6类.md`　构建溯源：`dataset-6class/build-stats.json`
> 本文所有数字均来自上述脚本的实际输出，未手工填写。

## 1 「6 类目」到底是什么（先说清这个概念）

系统病害本体是**五类四等级**（`backend/fusion.js` 的 `DEFECT_TYPES`）：
剥落掉块 / 裂缝 / 渗漏水 / 衬砌错台 / 白华析出。

**背景**在 `backend/train/build-samples.js` 里作为第 6 个类目出现
（`CLASSES = ['背景','裂缝','渗漏水','剥落掉块','衬砌错台','白华析出']`），
它表示「这块区域没有任何病害」，是训练时的**负样本**，不是一种病害。

因此本次补齐的含义是：

| 口径 | 数量 | 说明 |
|---|---|---|
| 训练集**类目**（含背景负样本） | **6** | 5 个病害类 + 1 个背景类，train 每类 ≥150 张 |
| YOLO 检测头类别数 `nc` | **5** | 背景不做检测类别，用**空标签文件**表达 |

> **为什么不把「背景」设成 nc 里的第 6 个类？**
> YOLO 是检测器，输出的是「框 + 类别」。给背景设一个类别，等于让模型去画一个
> 「这里没东西」的框，既无监督信号可依，也会和真实框抢位置，是明确的做法错误。
> 标准的负样本表达方式是「图片有、标签文件空」。本次 180 张背景图就是这样落盘的
> （`neg_*.jpg` + 0 字节 txt）。训练日志已实测确认：
> `906 images, 150 backgrounds, 0 corrupt`（上一版口径）/ 本版 1226 张时同样为
> `1226 images, 150 backgrounds, 0 corrupt`。

## 2 为什么必须补：补齐前后的覆盖对比

| 项目 | 补齐前（`dataset/`） | 补齐后（`dataset-6class/`） |
|---|---|---|
| 类别覆盖 | 3 类（Spalling / Crack / Leakage） | **5 类全覆盖** + 背景负样本 |
| 衬砌错台 | 0 张 / 0 框 | **415 张 / 415 框**（train） |
| 白华析出 | 0 张 / 0 框 | **225 张 / 411 框**（train） |
| 渗漏水实例占比 | 42.5% | **23.1%** |
| 图片 / 标签 / 框 | 330 / 330 / 530 | **1475 / 1475 / 3490** |

补齐前 YOLO 只能识别 3 类，而业务侧要判 5 类 —— 错台与白华永远检不出来，
`kg.js` 里那两条「错台/白华 → 成因 → 措施」推理链在检测入口就是断的。

## 3 数据来源（四类合并，逐图可溯源）

| 来源 | 张数 | 说明 |
|---|---|---|
| 实拍原图（`dataset/`） | 330 | 公开隧道病害数据集，仅覆盖裂缝/渗漏水/剥落掉块 |
| **实拍底图 + 合成缺陷** | 965 | 用实拍隧道影像做底图，贴入/叠加合成缺陷；底图原有实拍标注**按几何变换同步继承**，新增框由 `composeOne` 的紧致包围盒或错台带精确回填 |
| 纯程序化合成 | **0** | 已全部停用，理由见下方「为什么不再用程序化背景」 |
| 背景负样本 | 180 | 从实拍图裁出「不压任何标注框」的干净区域（真混凝土纹理）+ 程序化干净背景 |

> **为什么不再用程序化背景？**
> 第一版合成图有 15% 用 `synthesizer.makeBackground()` 的程序化衬砌纹理。做样例图复核时发现：
> 那是**平滑灰度渐变 + 几个柔和明暗斑**，和真实混凝土的骨料颗粒、污渍、施工缝完全不是一回事。
> 留着它有两个害处：① 错台/白华的合成图看起来像贴纸，评审一眼就出戏；
> ② 更糟的是模型可能学到「平滑底 = 缺陷」这种假线索。
> 实拍底图（`.cache/png/` 里 330 张）本来就可以重复复用，没必要用程序化背景凑数，所以这一版
> **全部改为实拍底图**（构建输出 `synthProcedural: 0`）。代价：13% 的合成图被重做，实例数
> 因为继承了更多实拍标注而从 3221 涨到 3490。

> **贴片类的框不是估值**：`composeOne()` 贴完后用 `tightBox()` 按 `alpha>40`
> 求实际可见范围的紧致包围盒，脚本直接换算成归一化 YOLO 框。框与像素严格对应。
> 贴片还会主动避开底图已有的实拍框（重叠 >25% 就重抽），避免一个框里塞两种病害。

### 衬砌错台没有用「贴片」，而是整幅几何错动

这是本次唯一一处**没有**走 synthesizer 贴片管线的类，理由是贴片做不出错台：

贴一块「错台纹理」长方形到实拍底图上，得到的只是一块**方形补丁**。人眼一看就是贴纸，
模型则会学到「带斑点的矩形 = 错台」这个假特征 —— 到真实影像上，任何矩形纹理
（模板痕迹、修补块、水渍边界）都可能误触发，属于典型的 shortcut learning。

改用的做法是**画布级位移**（`build-6class.js` 的 `applyLiningOffset`）：

1. 取一条横向「错台缝」，缝线以下整体横移 1.2%~6.2% 画布宽度；
2. 缝线本身压暗并羽化 2~5px，形成真实的错台阴影；
3. 下半段整体轻微提亮/压暗（两段衬砌表面朝向不同 → 受光不同）；
4. 标注框取「错动带」：宽 0.94W、高 0.18~0.35H。

这和真实错台的成像机制一致（一段衬砌相对另一段错动 → 横向贯通接缝 + 上下错位 + 缝线阴影），
比贴片忠实得多。底图继承的实拍框若中心落在缝线以下，会跟着同一位移量平移，框不会和像素错开。

### 诚实边界：错台 / 白华没有实拍标注

这两类**一张实拍标注都没有**，全部来自合成。所以：

- 它们在合成验证集上的 AP **不能**代表真实隧道里的表现；
- 本次同时产出 `metrics.real-only.json`（只含实拍图的 val 口径），
  其中这两类的 AP 必然为 0 —— 这不是 bug，是「真实世界性能尚未被验证」的如实记录；
- 要真正解决，仍需现场采集 + 人工标注这两类实拍图。本次没有条件完成，不做掩饰。

另外两点已知局限，一并说清：

- **白华析出的合成形态偏简单**：`synthesizer` 的 `白华析出` 绘制的是平滑高亮椭圆 + 竖向流挂，
  比真实钙质析出（不规则结垢、粉末感、边缘蔓延）简单得多。框位置是对的、概念是对的，
  但纹理真实度明显弱于裂缝/渗漏/剥落这三类实拍数据。若要提升，需要另写一个更贴近真实析出的
  渲染器（本次未做）。
- **可以用 `tools/yolo/make_sample_sheet.py` 自己看**：它会把 6 个类目各抽若干张训练图、
  连同 GT 框一起拼成 `数据样例-6类目.png`。判断数据能不能用，看这张图比看指标更直接。

### 样例自查

## 4 切分与各类规模

| 类目 | train 图片 | val 图片 | test 图片 | train 实例(框) |
|---|---|---|---|---|
| Spalling（剥落掉块） | 462 | 58 | 23 | 790 |
| Crack（裂缝） | 464 | 64 | 21 | 647 |
| Leakage（渗漏水） | 532 | 74 | 45 | 681 |
| LiningOffset（衬砌错台） | **415** | 40 | 20 | 415 |
| Efflorescence（白华析出） | **225** | 40 | 20 | 411 |
| 背景（空标签负样本） | **150** | 20 | 10 | — |
| **合计** | **1226** | **166** | **83** | **2944** |

- 5 个病害类 train 图片 **全部 ≥150 张**，加背景共 6 个类目均达标
  （`verify-6class.js` 的 L6 层自动判定，不通过会 exit 1）。
- 「图片数」和「框数」的排名不同，是因为多类共现：一张图可以同时有渗漏水和裂缝。
  检测任务看**框数**更准（见下一节）。
- val / test 里也有 `syn_*` 合成图：错台与白华没有实拍图，若 val 里不放合成图，
  这两类指标会直接是 NaN，质量门控无从判断。

### 防泄漏

- 实拍图沿用原 `dataset/` 的**按采集组切分**结果（同源序列不跨 train/val/test）。
- 合成图只从**同切分**的实拍图取底图：train 合成图只用 train 实拍图做底图，
  val / test 合成图只用各自切分的实拍图。
- 核验脚本按内容 sha1 跨子集比对，实测 **0 组**跨子集同内容。

## 5 类别平衡：渗漏水实例占比 42.5% → 23.1%

原数据集渗漏水框占比 42.5%（225/530），是 3 epochs 冒烟训练**把所有目标都判成
Leakage** 的直接原因之一。

本次用三条措施，并且都是可复算的硬判定：

1. **补齐少数类**：错台 +415 框、白华 +411 框，分母做大；
2. **实例级二次平衡**（`build-6class.js` 的 5b 步）：
   贴在实拍底图上的合成图会继承底图的实拍标注 —— 补错台的同时也在给裂缝/渗漏水加样本，
   所以只按「图片数」补一遍是不够的。脚本按**实例数**迭代校正，最多再补 320 张。
3. **欠采样硬阈值**：`verify-6class.js` 的 L5 层规定
   渗漏水实例占比 >30% 或 最多/最少类实例数比 >2.0 即判失衡并提示欠采样。

实测结果（L5 层自动判定）：

| 指标 | 值 | 阈值 | 结论 |
|---|---|---|---|
| 渗漏水实例占比 | **23.1%** | ≤30% | ✓ 无需欠采样 |
| 最多/最少类实例数比 | **1.92** | ≤2.0 | ✓ |

各病害类 train 实例占比：
Spalling 26.8% / Leakage 23.1% / Crack 22.0% / LiningOffset 14.1% / Efflorescence 14.0%。

> 欠采样这一步**没有触发**，不是漏做：补齐数据本身已把失衡压到阈值以内。
> 阈值和判定是脚本里的硬条件，不是口头结论。若后续加数据把渗漏水推回 30% 以上，
> L5 会直接判不通过并提示欠采样，不会悄悄放过。

## 6 复现命令

```bash
# 1) 实拍 JPEG → PNG 缓存（synthesizer 只吃 PNG；Node 侧无 JPEG 解码器）

# 2) 构建 6 类目数据集（每类目标 160 张，seed 固定可复现）
node tools/yolo/build-6class.js --target 160 --seed 2026

# 3) 六层核验（文件/图像/对应/内容/平衡/门槛）
node tools/yolo/verify-6class.js
```
